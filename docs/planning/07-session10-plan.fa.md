## نقطه‌ی داوری (درخواست Parsa: «اگر نتیجه نمی‌گیریم، یک بار داوری کن»)

بعد از ردیف ۴ یک بخش «داوری» در همین فایل نوشته می‌شود: آیا مسیر «قاعده‌ی ساختاری + holdout» هنوز عدد
می‌دهد یا سقف خورده (precision ~0.50 روی gold تک‌فایلی چهار مجموعه‌ی پشت سر هم = سیگنال سقف).
گزینه‌های روی میز اگر سقف بود: (الف) گیت precision را با تعریف «gold همسایه‌پذیر» بازنویسی نکنیم — عدد
همان است که هست؛ (ب) B′ (BM25/reranker) که سند ۰۶ مشروط گذاشته؛ (ج) پذیرش که ادعای اصلی task-success
است و precision فایل‌محور معیار غلطی برای packet چندفایلی است — یعنی فاز C تنها راه اثبات است.

## داوری (نوشته‌شده بعد از F52–F54، F25، ۵b، و اولین اجرای Config→Code)

**شواهد امروز، بی‌تعارف:**

| نوع تغییر | نمونه | نتیجه |
|---|---|---|
| anchor/نود جدید (موتور چیزی را «نمی‌دید») | F54 ثابت‌های SCREAMING_SNAKE؛ F51؛ F50؛ D-۱..۳ | همیشه خالص مثبت، بقیه‌ی مجموعه‌ها دست‌نخورده |
| حذف یک منبع نویز از fill/walker | F52 (شرط شواهد)، F53 (`.claude/`)، قبلاً F36′/F46/F47/F51b | همیشه خنثی یا منفی: slot آزادشده را حلقه‌ی ۳۶ با فایل بی‌ربط دیگری پر می‌کند |
| نود جدید با نام انگلیسی‌شکل | Config→Code v1 (`metric`، `dataset` از argparse) | holdout-ml 0.360→0.347، large 0.507→0.502 — همان حلقه‌ی ۳۶ |

**نتیجه:** precision فایل‌محور روی همه‌ی مجموعه‌های holdout (0.50±0.1 روی چهار مجموعه‌ی مستقل + private 0.60)
سقف خورده و سقف یک منبع دارد: **حلقه‌ی ۳۶ در `selector.rs`** — هر کلمه‌ی ≥۵ حرفی prompt (نه فقط identifier)
با `resolve_ranked` سراسری به اولین symbol هم‌نام می‌رسد و ۳۶ امتیاز می‌گیرد. سه بار جداگانه دست‌زدن مستقیم به آن
(F36′، F43، F46) روی large شکست، چون golds چندفایلی django به «همسایه‌ی اتفاقی» تکیه دارند که همین حلقه می‌آورد.

**آیا مسیر اشتباه است؟** مسیر «قاعده‌ی ساختاری + holdout + ratchet» درست کار می‌کند — هر جا موتور چیزی را
نمی‌دید، یک قاعده‌ی کوچک آن را دید و هیچ‌جا نشکست. چیزی که اشتباه است **انتظار رسیدن به 0.60 از این مسیر** است:
نیمی از فاصله سبک gold است (تک‌فایلی)، نیم دیگر حلقه‌ی ۳۶؛ و حلقه‌ی ۳۶ با ratchet روی large قفل شده.

**تصمیم (اختیار تام، قابل بازگشت):**
1. Config→Code را با قاعده‌ی «کلید config فقط با نام کدشکل حل می‌شود» تمام می‌کنم (v2). اگر روی ۸ مجموعه بی‌افت بود مرج.
2. بعد از آن، **یک** تلاش ساختاری روی حلقه‌ی ۳۶ با ابزار جدید که قبلاً نبود: resolve کلمات خام prompt (نه identifierها)
   فقط با **match دقیق نام** (نه fuzzy/stem) و فقط اگر آن نام در ≤۲ فایل ریپو باشد (df از `name_to_nodes`، بدون idf
   امتیازی — F39 رد شده بود چون امتیاز را دستکاری می‌کرد، این فقط «حل نکن» است). یک PR، ۸ مجموعه، ratchet.
   اگر large افتاد → ثبت به‌عنوان F55 رد‌شده و **حلقه‌ی ۳۶ رسماً بسته** می‌شود تا فاز C.
3. فاز C (task-success با مدل) تنها معیاری است که «همسایه‌ی اضافی» را جریمه نمی‌کند و «فایل گم‌شده» را جریمه می‌کند
   — همان چیزی که recall≈1 ما را می‌سنجد. یعنی ادعای اصلی پروژه احتمالاً از precision فایل‌محور قوی‌تر است، ولی
   بدون کلید ثابت‌نشدنی است. **این وابستگی به Parsa واقعی و تنها است.**

## تصمیم‌های بعد از داوری (تأیید Parsa، ۱۴ سپتامبر، «اختیار تام»)

1. **ratchet جدید (جایگزین «فقط بالا، حتی ۰.۰۰۳»):** یک مجموعه فقط وقتی افت دارد که precision بیش از **۰.۰۲**
   پایین بیاید، یا recall بیش از ۰.۰۱، یا forbidden جدید بیاید. کمتر از آن یعنی یک فایل در یک تسک (۱۲ تسک: ۰.۰۱۴)
   و سیگنال نیست. هر افت زیر آستانه هم probe و ثبت می‌شود (یادگیری)، ولی مرج را نمی‌بندد. holdoutها و مجموعه‌های
   تنظیم یک قانون دارند.
2. **precision-tuning بسته شد.** F48، F30/F31، و «تلاش آخر روی حلقه‌ی ۳۶» انجام نمی‌شوند؛ اعداد holdout به‌عنوان
   عدد پروژه ثابت‌اند تا فاز C. تغییرات موتور فقط از جنس «چیزی که موتور نمی‌دید» (نود/anchor/گرامر/دامنه‌ی جدید).
3. بنچمارک ۸ مجموعه به GitHub Actions (workflow دستی + comment روی PR) منتقل می‌شود.
4. بعد از آن: فاز C ارزان (Haiku، `ANTHROPIC_BASE_URL`) آماده می‌شود؛ ارزیابی انسانی ۱۰ سؤال روی ریپوی B2B با
   Parsa (بدون API) به‌عنوان جانشین ارزان فاز C.
