## چه چیزی یاد گرفتیم (خلاصه‌ی روش)

- **همه‌ی فیکس‌های موفق «حذف seed/edge غلط» بودند؛ همه‌ی شکست‌ها «دستکاری امتیاز fill».** روش کار: probe
  (`NM_PROBE_EDGES=1`، `NM_PROBE_RANK=1`) → علت ساختاری → یک قانون → سه (حالا چهار) مجموعه → ratchet فقط بالا.
- **اختلاف باقی‌مانده تا ۰.۶۰ روی large/holdout-2 عمدتاً سبک gold است** (تک‌فایل vs همسایه) نه باگ موتور — سه
  تلاش fill-tuning رد شد (F36′/F46/F47، همه در findings). دیگر روی این خط وقت نگذار مگر با سیگنال جدید.
- **oracle هم می‌تواند باگ داشته باشد** (تعریف C-style را نمی‌شناخت) — عدد oracle روی زبان جدید را قبل از
  تفسیر، با یک probe دستی چک کن.

## تله‌های تازه‌ی این بخش

- **حین اجرای پس‌زمینه‌ی cargo test، هیچ فایل سورسی را ویرایش نکن** — یک بار holdout با کد نیمه‌کاره کامپایل نشد
  و خروجی خالی داد (اشتباه گرفتم که «عدد نیامد»).
- `perl -0pi` روی فایل‌های CRLF این ریپو match نمی‌کند؛ برای فایل‌های CRLF از Edit tool یا `sed -i 'Ns/…/'` خط‌محور.
- `gh pr checks --watch` اگر قبل از شروع checkها زده شود بلافاصله با «no checks reported» برمی‌گردد — `sleep 90` قبلش.
- `python3`/`python` در Git Bash این ماشین به stub ویندوز می‌رود؛ `node` و `py -3` کار می‌کنند.

## تله‌های تازه (ادامه)

- CI clippy را با `-D warnings` می‌زند؛ لوکال هم همین را بزن: `cargo clippy --all-targets -- -D warnings` (یک بار #64 قرمز شد).
- `LNK1318`/`LNK1180` (PDB/دیسک): `target/debug/incremental` (۷–۸G) و pdbهای کهنه‌ی `target/debug/deps` قابل حذف‌اند؛ دیسک این ماشین ~۹G آزاد دارد.

## درس بخش D-۳ (برای هر holdout تازه)

سه یافته‌ی D-۳ اصلاً ربطی به overlay نداشتند: walker `examples/` را مطلقاً حذف می‌کرد (keras-io = هیچ)، آینه‌های
ipynb/md بر کد برنده می‌شدند، و stem بلند فایل هیچ‌وقت از جست‌وجوی ۱۲تایی symbol بیرون نمی‌آمد. **قبل از تفسیر عدد
یک holdout جدید، اول `doctor`/probe بزن که فایل‌های gold اصلاً ایندکس شده‌اند** — recall 0 روی ۵/۵ یعنی زیرساخت، نه
رتبه‌بندی. قاعده‌ی «کلمه‌ی کدشکل = stem فایل» یک بار holdout-2 را ۰.۰۰۳ پایین آورد (`roi_heads`) — به ≥۳ بخش محدود شد.
