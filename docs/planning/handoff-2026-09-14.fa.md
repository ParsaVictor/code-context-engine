## ۵a — نتیجه (خلاصه؛ کامل در stage5-findings.fa.md)

| معیار | dev (۴ ریپو) | holdout (django+ultralytics) | گیت |

| precision | 0.856 | **0.146** | ≥0.60 ✗ |

**نتیجه‌گیری: overfit سیستماتیک تأیید شد.** precision holdout دقیقاً برابر عدد شروع پروژه قبل از مرحله ۴ است.

(کلمه‌ی عمومی prompt یا synonym چندزبانه‌ی ساخته‌شده برای واژگان dev، با symbol تصادفی هم‌نام در ریپوی بزرگ
برخورد می‌کند). **هیچ فیکسی زده نشد** — طبق تصمیم Parsa (تأیید در همین session)، طبق برنامه ادامه داده شد؛
فیکس واقعی این‌ها فاز ۷ است.

## ۵c — نتیجه (خلاصه)

روی ultralytics (۹۳۱ فایل): index 2142ms، حافظه‌ی peak ~82MB، latency سرتاسری هر پرسش p50≈280ms/p95≈464ms
(n=10). گیت داخلی `l1_p95≤50ms` (روی کد خودِ این پروژه، ۴۷۹ فایل) با ۲ms فاصله pass شد (48ms). گیت prompt
خصمانه (۲MB) pass شد (24.8s/25.1s < 30s). مقایسه‌ی «≤۱.۵× baseline روی ریپوی بزرگ» **اندازه‌گیری‌نشده ماند**
— هیچ baseline بزرگی از v0.9.0 وجود ندارد که با آن مقایسه شود؛ حدس زده نشد.

نکته‌ی روش‌شناسی (در حافظه هم ثبت شد): spawn مستقیم باینری از طریق PowerShell `Process` روی ultralytics
۳۳ دقیقه با CPU صفر گیر کرد؛ همان دستور از طریق Bash ۱۱.۷ ثانیه طول کشید. برای اندازه‌گیری‌های بعدی همیشه
از طریق Bash اجرا شود، نه PowerShell `System.Diagnostics.Process`.

(اثبات task-success با `ANTHROPIC_API_KEY` + تصمیم F25) شروع شود.

## فاز ۶ — پیش‌ساخت (همین session، موازی با انتظار ۵b)

دو نقص در harness موجود پیدا و رفع شد ([PR #46](https://github.com/ParsaVictor/code-context-engine/pull/46)،
بدون لمس کد موتور/retrieval):

1. `neuromesh eval --tasks --executor model` از قبل وجود داشت (حافظه‌ی session قبل غلط می‌گفت هرگز اجرا نشده)
   ولی هیچ baseline «کل فایل‌های گلد» یا «grep ساده»ای نداشت. فلگ `--context packet|whole-gold-files|grep`
   اضافه شد؛ `effective_tokens`/`success_per_1k_tokens` حالا واقعاً به همان context ای که به مدل فرستاده شده
   حساب می‌شود، نه همیشه توکن packet.
2. **مهم‌تر:** هیچ‌کدام از ۲۱ تسک واقعی dev (express/nanoGPT/vit-pytorch/fastapi-template) دستور `verify`
   ندارند — همه سؤالی‌اند («این چطور کار می‌کند؟»)، نه فیکس‌کردنی. بدون رفع این، اجرای `--executor model`
   روی این‌ها بی‌صدا به oracle برمی‌گشت و هیچ سیگنال جدیدی از مدل واقعی نمی‌گرفت. مسیر QA-judge اضافه شد:
   مدل جواب می‌دهد، بعد یک تماس دوم (داور) PASS/FAIL می‌دهد که آیا جواب دقیقاً `needs` را توضیح داده.
   **محدودیت مستندشده در کد:** گلد جواب مرجع ندارد (فقط اسم symbol)، پس داور از دانش خودش قضاوت می‌کند —
   عدد QA-judge را جهت‌دهنده بدان، نه هم‌قوت مسیر verify. با `--provider mock` (بدون کلید API) هر دو مسیر
   (verify و qa-judge) روی هر سه حالت context تست شد — کار می‌کند.

**هنوز باز، برای همان session‌ای که کلید API دارد:** آیا داور باید مدل/instance متفاوتی از پاسخ‌دهنده باشد
(جلوگیری از خودارزیابی نرم)؛ آیا برای زیرمجموعه‌ای از تسک‌های dev/holdout ارزش دارد `verify` واقعی نوشته شود
(دقیق‌تر از QA-judge). این‌ها تصمیم لازم دارند، حدس زده نشدند.

## قوانین (تکراری از session قبل + ۱ مورد جدید)

- قبل/بعد هر تغییر در `scripts/fetch-third-party.sh` یا هر فایل مشترک: هم دستور dev (`bash scripts/fetch-third-party.sh && NM_THIRD_PARTY=1 cargo test ... third_party_gold`) هم اگر مرتبط بود دستور holdout را بزن، عدد قبل/بعد را در PR بگذار.
- **جدید:** برای اندازه‌گیری زمان/حافظه‌ی باینری release، از Bash استفاده کن، نه PowerShell `System.Diagnostics.Process` (گیر می‌کند — دلیل دقیق پیدا نشد، احتمالاً تعامل با sandbox این محیط).
- **جدید:** باینری release برای مقایسه با baseline «v0.9.0 fast engine» را **بدون** `--features embeddings` بساز؛ آن فلگ تلاش می‌کند مدل MiniLM را بارگذاری کند و می‌تواند به‌جای چند ثانیه، دقیقه‌ها طول بکشد یا گیر کند.
- گلد holdout (`tests/third_party/holdout/`) قفل است — حتی وقتی بعد از اجرا معلوم شد یک forbidden_file انتخابی اشتباه بود (F: recorder.py، metrics.py در stage5-findings)، گلد را عوض نکن؛ فقط در findings توضیح بده.
- بقیه‌ی قوانین (CRLF اسناد، `gh pr view --json mergeable`، مانیتور ≤۱۵ دقیقه، `CARGO_BUILD_JOBS=2`، mutation-test هر قاعده) بدون تغییر از handoff-2026-09-13c.
