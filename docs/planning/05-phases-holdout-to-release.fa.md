# فازبندی از پایان مرحله ۴ تا انتشار (نوشته‌شده ۱۳ سپتامبر ۲۰۲۶، پایان session 8)

این سند مسیر رسمی پروژه از این‌جا به بعد است. هر session با این سند و آخرین handoff شروع می‌شود.
وضعیت شروع: main = `003d243`؛ ریپوهای واقعی (dev): recall 1.000 / precision 0.856 / forbidden 0 / oracle 21/21 / strict 20؛
گیت ریلیز `precision_min` 0.383 (F25)؛ task-success با مدل واقعی هرگز اجرا نشده؛ هیچ holdout ای وجود ندارد.

## چرا این ترتیب

مرحله ۴ precision را روی ۴ ریپو از 0.146 به 0.856 رساند، ولی هر ۱۲ قاعده با نگاه به همان ۴ ریپو نوشته شد.
عدد 0.856 «عدد پروژه» نیست تا وقتی روی ریپوی **نادیده** تکرار شود. پس اول تعمیم را می‌سنجیم، بعد ادعای اصلی
(task success با مدل واقعی)، بعد عمومیت را گسترش می‌دهیم، و آخر منتشر می‌کنیم. هیچ بهبود precision دیگری
روی dev شروع نمی‌شود تا فاز ۵ تمام شود — چون ممکن است فقط overfit عمیق‌تر باشد.

## اصل holdout (حاکم بر همه‌ی فازها)

- **dev** = ۴ ریپوی فعلی (`tests/third_party/`) — هر تنظیمی مجاز.
- **holdout** = ریپوهایی که هرگز روی آن‌ها تنظیم نمی‌کنیم — فقط اندازه‌گیری.
- گلد holdout **قبل از اولین اجرا** از روی خواندن کد نوشته و کامیت می‌شود (عمومی) یا hash اش ثبت می‌شود (خصوصی). نویسنده‌ی گلد packet را قبل از قفل شدن گلد نمی‌بیند.
- اگر روی holdout افت دیدیم و خواستیم فیکس کنیم: آن ریپو به dev منتقل می‌شود و holdout جدید لازم است (چرخش). هیچ‌وقت روی holdout تنظیم نمی‌کنیم و بعد همان را «holdout» گزارش نمی‌دهیم.
- هر فاز: اول گلد/تست، بعد کد؛ mutation-test هر قاعده (قاعده‌ی بی‌اثر حذف می‌شود)؛ ratchet فقط بالا؛ تست امنیت؛ عدد قبل/بعد در هر PR.

## فاز ۵ — اثبات تعمیم (اولویت مطلق)

### ۵a — holdout عمومی
- ۲ ریپوی گیت‌هاب که تا حالا در این پروژه دیده نشده‌اند: یک بک‌اند با فریم‌ورک/زبان متفاوت از express/fastapi (پیشنهاد: Django یا Go) و یک ریپوی ML غیر nanoGPT/vit-pytorch (پیشنهاد: `ultralytics` — بزرگ است و ادعای «universal ML» را می‌سنجد).
- pin با rev در `tests/third_party/holdout/repos.toml`؛ گلد ۱۰ سؤال هر ریپو در `gold_tasks.toml` + `tasks.toml` (needs/forbidden)؛ **کامیت گلد قبل از هر اجرا** (PR جدا با عنوان «holdout gold — no engine run»).
- اجرا با همان `third_party_gold` (پارامتر مسیر holdout)؛ **بدون هیچ تغییر کد**.
- گیت: recall ≥ 0.90، precision ≥ 0.60، forbidden 0. زیر 0.40 = overfit؛ مرحله ۴ بازبینی می‌شود (کدام قاعده‌ها روی نادیده‌ها می‌شکنند — probe هر شکست).

### ۵b — holdout خصوصی (پروژه‌ی B2B تیم)
- Parsa/تیم ۱۵–۲۰ سؤال واقعی توسعه‌دهنده + فایل‌های جواب (و فایل‌های ممنوع) را در یک `gold_tasks.toml` محلی می‌نویسند (قالب همان `tests/third_party/express/gold_tasks.toml`). Claude تا قفل شدن گلد packet نمی‌بیند.
- کد خصوصی هرگز وارد ریپوی عمومی نمی‌شود؛ فقط اعداد، failure classes و توصیف بی‌نام اشکال‌ها در `stage5-findings.fa.md`.
- گیت: همان ۵a. اشکال‌های فریم‌ورک/زبان خودمان اینجا بیرون می‌آید — این هدف است.

### ۵c — مقیاس و سرعت
- روی ریپوی بزرگ (B2B یا ultralytics): زمان index، حافظه، L1 p50/p95، prompt خصمانه؛ مقایسه با پایه‌ی v0.9.0 (12/26 ms روی ۲۰۰ فایل). مرحله ۴ هفت پاس به مسیر seed اضافه کرد (~۱۰٪ کندتر روی prompt خصمانه) و latency معمولی دوباره اندازه‌گیری نشده.
- گیت: p95 ≤ SLO فعلی (50 ms) روی ۲۰۰ فایل؛ روی ریپوی بزرگ ≤ 1.5× پایه؛ prompt خصمانه < 30 s روی ماشین خالی. اگر رد شد: پروفایل، نه حدس.

خروجی فاز ۵: اولین عدد صادقانه‌ی «روی ریپوی نادیده» + عدد مقیاس. تا این دو نیاید، فاز ۷ شروع نمی‌شود.

## فاز ۶ — اثبات ادعای اصلی: task success با مدل واقعی

- `neuromesh eval --tasks --executor model` با `ANTHROPIC_API_KEY` روی ۲۱ task dev + taskهای holdout؛ دو baseline: «کل فایل‌های گلد» و «grep ساده».
- گیت: task_success ≥ 0.5 (گیت ریلیز موجود) و success-per-1k-token بهتر از baseline «کل فایل».
- **F25** همین‌جا: تعریف گیت ریلیز با تصمیم Parsa (پیشنهاد: سلول no_seed از میانگین precision خارج؛ گلد `physarum_usage` به ۱۲ فایل واقعی یا سؤال usage معاف) تا گیت رسمی معنی‌دار و سبز شود.
- خروجی: اولین ادعای قابل دفاع «packet کافی است و مدل با آن کار را درست انجام می‌دهد».
